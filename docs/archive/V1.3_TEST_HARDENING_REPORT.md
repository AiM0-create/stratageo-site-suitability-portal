## Problem: OpenAI Import-Chain Fragility

### Symptoms (pre-fix)

Running `pytest -q` produced 5 collection errors before any tests ran:

```
ERROR tests/test_critic.py
ERROR tests/test_results.py
ERROR tests/test_scoring.py
ERROR tests/test_v1031_patches.py
ERROR tests/test_viability_gate.py
!!!!!!!!!!!!!!!!!!! Interrupted: 5 errors during collection !!!!!!!!!!!!!!!!!!!
```

Additionally, `test_water_tag_hotfix.py::test_is_water_tag_importable_via_jobs` failed because `jobs.py` was not importable.

### Root cause

| Module | Problematic line | Used only in |
|---|---|---|
| `app/engine/results.py` | `from openai import AsyncOpenAI` (line 14) | `write_explanations()` async function |
| `app/services/critic.py` | `from openai import AsyncOpenAI` (line 17) | `critique_analysis()` async function |

These top-level imports caused import failures whenever `openai` was not installed, regardless of whether the LLM call paths were ever invoked. The following import chains propagated the failure:

```
test_critic.py → critic.py → openai ❌
test_results.py → results.py → openai ❌
test_scoring.py → results.py → openai ❌
test_v1031_patches.py → jobs.py → results.py → openai ❌
test_viability_gate.py → jobs.py → results.py → openai ❌
test_water_tag_hotfix.py → jobs.py → results.py → openai ❌
```

### Fix applied

Made both OpenAI imports **lazy** — moved them inside the functions that actually make LLM calls.

**`app/engine/results.py`:**
```python
# Before (module-level, broke all importers):
from openai import AsyncOpenAI

# After (lazy, inside write_explanations):
async def write_explanations(...):
    from openai import AsyncOpenAI  # lazy import — only needed when LLM call fires
    ...
```

**`app/services/critic.py`:**
```python
# Before (module-level, broke all importers):
from openai import AsyncOpenAI

# After (lazy, inside critique_analysis):
async def critique_analysis(...):
    try:
        from openai import AsyncOpenAI  # lazy import — only needed when LLM call fires
        ...
```

**Result:** Importing these modules at test collection time no longer requires `openai`. The import error only fires when an actual LLM call is attempted without the package installed — which is the correct behavior for a fail-soft optional dependency.

## Endpoint Auth Analysis

The new endpoints `GET /api/v2/analyses/{jobId}/evidence` and `GET /api/v2/analyses/{jobId}/evidence.json` follow the **same security model** as the existing analysis polling endpoint (`GET /api/v2/analyses/{jobId}`).

The `SecurityMiddleware` in `security.py` exempts GET requests on `/api/v2/analyses/*` from the shared-token gate via:
```python
is_poll = path.startswith("/api/v2/analyses/") and request.method == "GET"
if protected and not is_poll ...:
    # token check only here
```

**This is the designed behavior** — polling does not require the token so the UI stays responsive. Evidence retrieval follows the same pattern.

**No per-user job isolation exists** — this is the current architecture (shared-token global gate, no per-user analysis ACLs). Someone who knows a valid job UUID can access its evidence. This is the same for the existing polling endpoint and was not changed by v1.3.0.

**Access barrier:** Job IDs are server-minted UUID4s (`uuid.UUID(job_id)` validation in the router). Without a valid UUID, the endpoint returns 400.
