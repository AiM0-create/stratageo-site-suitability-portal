# v1.3.0 Reproducibility Limitations

This document distinguishes three reproducibility levels and states honestly what v1.3.0 achieves.

---

## Three Reproducibility Levels

### Level 1: Deterministic Planning (v1.2.0 ✅)
Same prompt → same factor table, same weights, same `planningFingerprint`.

Achieved by: canonical archetype registry + deterministic planner override + temperature=0 + seed=42.

**Stable across sessions:**
- `archetypeKey`
- factor keys and weights
- `planningFingerprint`
- `planningMode = "deterministic"`

**May vary:**
- `specFingerprint` (includes LLM explanation text)
- candidate rankings (depend on live OSM/Places data)

---

### Level 2: Audit Reproducibility (v1.3.0 ✅)
A client can inspect exactly what data was queried, what features were counted, how every score was computed, and which cells/candidates were excluded.

Achieved by: `EvidenceTrail` schema with provider query records, factor evidence, candidate evidence, and exclusion ledger.

**What can be audited:**
- Which providers were queried (OSM, Google Places, ORS)
- Feature counts per factor per candidate
- Normalized score and weighted contribution per factor
- H3 cells removed by each mask (water, railway, corridor, etc.)
- Candidate exclusion reasons
- Scoring formula description + weight sums
- Study area geometry hash

**What cannot be fully audited:**
- The actual OSM/Places API responses (not stored — only summarized counts)
- Individual H3 cell feature counts (batch level only)
- Whether OSM data changed between the run and the audit

---

### Level 3: Full Data Replay (not yet implemented ❌)
Re-run the exact same analysis with a cached snapshot of OSM and Places data and get bit-identical output.

**Requirements for full replay (future work):**
1. Cache the complete Overpass API responses per (tags, bbox) pair to GCS
2. Cache Google Places responses per (types, keyword, bbox) pair
3. Re-run the analysis pipeline against the cached snapshot instead of live providers
4. Store the cache keys in `EvidenceTrail.dataSnapshot`

---

## Live Data Sources and Their Instability

| Source | When it changes | Impact on reproducibility |
|---|---|---|
| OpenStreetMap Overpass | Continuous edits by mappers | Feature counts change; may affect scores |
| Google Places | Continuous business additions/closures | Competition layer counts change |
| ORS routing | Network topology updates | Isochrone boundaries may shift |
| Nominatim geocoding | Place name database updates | Study area polygon may shift slightly |

---

## Honest Labeling

v1.3.0 uses this language in `evidenceTrail.limitations`:

> "This evidence trail is AUDIT REPRODUCIBLE — it records what data was queried and how scores were computed. Full replay depends on cached provider responses and is not yet implemented."

And in the Evidence Tab UI:

> "⚠ Audit reproducible — the plan and scoring formula are stable. Full data replay requires cached provider snapshots."

We do NOT claim:
- "Fully replayable"
- "Deterministic output"
- "Same results every time"

We DO claim:
- "Same factor schema every time" (deterministic planning — v1.2.0)
- "Fully auditable scoring methodology" (evidence trail — v1.3.0)
- "No secrets in evidence export" (guaranteed by `safe_dict()` + `_scrub_secrets()`)
