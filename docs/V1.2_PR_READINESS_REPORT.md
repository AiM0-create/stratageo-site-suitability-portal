### specFingerprint difference — expected and harmless

The `specFingerprint` differs because it hashes the **full spec content** including LLM-contributed text fields: the `objective` wording, study area description text, feasibility explanation, and plan assumptions — all of which naturally differ between LLM calls. This is by design.

The `planningFingerprint` hashes only structural parameters (normalized prompt + archetype key + schema hash + engine version + cost mode) and is **perfectly stable**. The `planningFingerprint` is the correct stability guarantee for the framework/planning phase.

**Verdict: All structural/scoring fields are stable. ✅**

## Known Remaining Non-Determinism Sources

| Source | Type | Mitigation |
|---|---|---|
| External OSM data updates | Live data | Disclosed via `dataSnapshotTime`; fingerprint changes with data |
| Google Places ranking changes | Live data | POI counts may differ day-to-day |
| Overpass timeout / data variation | Network | Fallback notes in result; graceful degradation |
| ORS route failures | Network | Engine falls back to Euclidean proxy; disclosed |
| OpenAI seed reproducibility | LLM | OpenAI docs: "mostly deterministic" — backend structural validation is the guarantee |
| Study area locality enumeration | LLM (text) | LLM still enumerates places for geocoding; different runs may pick slightly different place name lists |
| `specFingerprint` varies with LLM text | LLM (text) | Expected — `planningFingerprint` is the structural stability hash |
| Geocoding ambiguity ("Ruby Crossing") | Geocoding | Nominatim/Google may return slightly different coordinates; study area polygon may vary |
